# 健康打卡 MVP 功能规格书

> **版本**: v1.0 | **日期**: 2026-07-29 | **作者**: 析客（需求分析师）| **状态**: 草稿

---

## TL;DR

健康打卡是一款面向个人用户的健康管理 App，核心差异化在于**采购→库存→饮食记录全链路闭环**。MVP 阶段以用户为唯一用户，聚焦「5 秒记录法则」降低饮食记录摩擦，通过 Mifflin-St Jeor 公式自动计算热量预算，结合 OCR 小票识别和营养缺口推荐实现智能饮食决策。首版覆盖：邮箱登录、目标设定、仪表盘、饮食记录、食物库搜索、体重曲线、自建食物（P0，8 个需求，预估 5 周）；后续逐步叠加库存管理、OCR、推荐引擎和运动记录。食物库采用三层策略：FatSecret API（主力，中文覆盖好、5000次/天免费）→ Open Food Facts（兜底）→ 自建食物库。完全免费，Android 原生（Jetpack Compose）+ Supabase 后端。

## 1. 产品目标

本版本确立三个清晰、正交的产品目标，所有 P0 需求必须至少服务其中一个目标：

| # | 目标 | 衡量方式 | 目标值（MVP 阶段） |
|---|---|---|---|
| **G1** | 极低记录摩擦——饮食记录 ≤ 5 秒完成 | 从点击大「+」到记录完成的时间（埋点 `meal_logged` 的 duration 字段） | 中位数 ≤ 5 秒 |
| **G2** | 全链路闭环——采购→库存→消耗可追溯 | 库存物品至少 50% 被关联到饮食记录中（关联率） | ≥ 50%（P1 上线后） |
| **G3** | 数据驱动自我调节——用户能通过仪表盘感知热量状态 | 每日至少 1 次仪表盘查看（`app_session_start`），且在热量超标/不足时次日有行为调整 | 日活会话 ≥ 2 次；超标后次日摄入回归预算 ±15% 范围内的概率 ≥ 60% |

> **正交性说明**: G1 关乎操作效率，G2 关乎数据完整性，G3 关乎行为改变——三者互不重叠，各自驱动不同的设计决策。

## 2. 用户故事

### 故事 1：晨间称重 + 仪表盘速览（≤ 30 秒）

> 用户早上起床，站上体重秤，打开 App 输入体重，仪表盘首页显示「今日剩余 1,680 大卡」的大数字，绿色进度条表示还可以放心吃。快速扫一眼昨天的饮食列表，确认没问题后锁屏开始新的一天。

**对应需求**: REQ-001, REQ-002, REQ-003, REQ-006  
**验收核心**: 从 App 打开到看到今日剩余热量 ≤ 3 秒（冷启动含登录态恢复）

### 故事 2：工作日三餐快速记录（每餐 ≤ 5 秒）

> 中午在食堂吃完饭，用户打开 App，点大「+」按钮，在弹出的搜索框中输入「米饭」，结果列表第一条就是上次吃过的米饭（150g），点击即完成记录。系统自动从今日预算中扣除 174 大卡，仪表盘数字实时更新。

**对应需求**: REQ-003, REQ-004, REQ-005, REQ-007  
**验收核心**: 搜索→选择→确认，三步完成，全程 ≤ 5 秒

### 故事 3：周末采购 → OCR 录入（≤ 1 分钟）

> 用户周六去超市买了鸡胸肉、西兰花、牛奶等食材，结账后打开 App 拍下购物小票。ML Kit OCR 自动识别出商品名称和数量，一键导入库存。系统显示库存清单，并标注每种食材的热量密度。

**对应需求**: REQ-010, REQ-011, REQ-012（OCR 为 P2）  
**验收核心**: P1 手动录入 ≤ 30 秒/种食材；P2 OCR 识别准确率 ≥ 85%（商品名+数量）

### 故事 4：里程碑达成 → 奖励自己

> 用户设定目标：「减重 5kg → 买一双新跑鞋」。当体重记录显示从起始 70kg 降到 65kg 时，App 弹出全屏成就卡片，金色动画庆祝达成。用户截图分享给朋友。

**对应需求**: REQ-009  
**验收核心**: 里程碑触发准确率 100%（体重数据自动比对，无遗漏）

### 故事 5：一周回顾 → 数据驱动自我调节

> 周日下午，用户打开体重曲线，看到过去 7 天体重从 68.2kg 稳步下降到 67.5kg。饮食记录显示平均每天摄入 1,550 大卡（预算 1,680），蛋白质偏少。决定下周增加鸡胸肉比例。

**对应需求**: REQ-003, REQ-006  
**验收核心**: 7 日趋势图数据完整，无断点

## 3. 用户研究洞察

> 以下洞察来自用户研究员瑞思的深度研究，经需求分析整合为设计约束。

| # | 洞察 | 设计约束 |
|---|---|---|
| **I1** | **5 秒法则**：每多一步操作，日活掉 20-30%。饮食记录的留存关键在于"快到不觉得在记录" | 搜索→点击→完成，三步以内；大「+」按钮必须拇指可达（FAB 右下角）；最近食物优先展示 |
| **I2** | **库存→饮食闭环是真正的差异化**：现有 App 只做饮食记录，但没人打通"买了什么→还剩什么→该吃什么" | P1 必须实现库存手动录入 + 饮食联动扣减，P2 OCR 进一步降低录入摩擦 |
| **I3** | **运动不计入预算，但需独立正反馈**：用户不希望「运动换来的热量额度」稀释减肥目标，但运动本身应有成就感 | 运动记录独立展示，不计入热量预算；连续运动天数（streak）独立追踪 |
| **I4** | **三个不做**：社交功能（增加焦虑）、AI 教练/Chatbot（MVP 过度设计）、复杂运动跟踪（手环生态已饱和） | Non-goals 明确列入，防止范围蔓延 |
| **I5** | **单人场景就是验证场景**：用户自己用满 4 周，亲身感受所有痛点，比任何用户访谈都真实 | MVP 阶段所有埋点优先服务单人行为分析，不设计多用户/家庭组 |

## 5. 数据依据

> 以下指标来自数据分析师数析的建模与行业基准研究。

### 5.1 北极星指标

**WER（周有效记录用户数）**：自然周内完成 ≥ 5 天有效饮食记录（每天至少记录 2 餐）。

- MVP 阶段 WER = 1（用户自用），目标达成率 ≥ 80%（即 4 周中 ≥ 3 周达标）

### 5.2 关键行为指标

| 指标 | 定义 | 目标（MVP） | 行业基准 |
|---|---|---|---|
| Day 1 留存 | 首日完成 ≥ 1 次饮食记录 | ≥ 90%（单人场景，等价于首日使用） | 35-40% |
| Day 7 留存 | 第 7 天仍有饮食记录 | ≥ 70% | 32% |
| Day 30 留存 | 第 30 天仍有饮食记录 | ≥ 50% | 14% |
| 日均记录次数 | 平均每天饮食记录条数 | ≥ 2.5 次 | ~2.0 次 |
| 记录耗时中位数 | 从点击「+」到确认完成 | ≤ 5 秒 | ~12 秒（竞品估算） |

### 5.3 MVP 埋点事件（Top 8）

| # | 事件名 | 触发时机 | 关键参数 |
|---|---|---|---|
| E1 | `onboarding_complete` | 完成首次目标设定 | 年龄、性别、BMI、目标体重差 |
| E2 | `meal_logged` | 完成一次饮食记录 | 餐次类型（早/午/晚/加餐）、热量、耗时（ms）、是否从库存扣减 |
| E3 | `weight_recorded` | 完成一次体重记录 | 体重值、与前次差值 |
| E4 | `app_session_start` | App 冷启动/热恢复 | 会话开始时间 |
| E5 | `calorie_budget_status` | 每次打开仪表盘时计算 | 剩余/总预算、蛋白/碳水/脂肪进度% |
| E6 | `milestone_achieved` | 体重达到自定义里程碑 | 里程碑名称、达成耗时（天） |
| E7 | `share_triggered` | 用户触发分享 | 分享内容类型（里程碑/体重曲线/饮食总结） |
| E8 | `streak_updated` | 连续记录天数变化 | 当前连续天数、是否新纪录 |

### 5.4 健康预警规则

- **触发条件**: 连续 3 天日均热量摄入 < 800 大卡
- **预警方式**: 仪表盘顶部温和提示「你最近吃得有点少，身体需要足够能量哦」
- **不做的**: 不弹窗阻断、不强制、不报警——仅温和提示

### 6.1 P0 — MVP v1.0（8 个需求，5 周）

| 编号 | 需求 | 优先级 | 验收标准 | 估算 |
|---|---|---|---|---|
| **REQ-001** | **邮箱注册与登录** | P0 | **Given** 用户首次打开 App **When** 输入邮箱+密码并点击注册 **Then** Supabase Auth 创建账户、发送验证邮件、自动登录进入目标设定页。**Given** 已注册用户 **When** 输入邮箱+密码登录 **Then** 恢复上次会话状态进入仪表盘。**Given** 已登录用户关闭 App 后重新打开 **When** Token 未过期 **Then** 自动恢复登录态，无闪烁。 | 3 天 |

| **REQ-003** | **仪表盘首页** | P0 | **Given** 用户已设定目标且今日有饮食记录 **When** 打开 App **Then** 展示：① 顶部「今日剩余 X,XXX 大卡」大数字（剩余 ≤ 200 红色，200-500 黄色，> 500 绿色）；② 今日饮食列表（按时间倒序，显示食物名+热量+餐次标签）；③ 三大宏量进度条（蛋白/碳水/脂肪，各显示 已摄入/目标 和百分比进度条）；④ 右下角大「+」FAB 按钮。**Given** 今日无记录 **When** 打开仪表盘 **Then** 显示空态引导「记录你的第一餐吧」。**Given** 热量超标 **When** 剩余为负数 **Then** 数字变红并显示「已超出 XXX 大卡」。 | 5 天 |
| **REQ-004** | **饮食记录（三餐+加餐）** | P0 | **Given** 用户点击大「+」按钮 **When** 弹出食物搜索界面 **Then** 顶部搜索框自动获焦，键盘弹起。**Given** 用户在搜索框输入关键词 **When** 输入 ≥ 1 个字符 **Then** 实时返回匹配结果（Open Food Facts + 自建食物库），每条显示食物名+每 100g 热量。**Given** 用户点击某食物 **When** 进入数量选择页 **Then** 默认值 100g，支持加减按钮或手动输入，实时显示总热量，选择餐次（早/午/晚/加餐）。**Given** 用户确认 **Then** 记录保存，仪表盘数据实时更新，返回仪表盘。全程 ≤ 5 秒。**Given** 用户想删除一条记录 **When** 在仪表盘饮食列表中左滑 **Then** 出现删除确认，确认后热量恢复。 | 6 天 |
| **REQ-005** | **食物库搜索（FatSecret + Open Food Facts）** | P0 | **Given** 用户在食物搜索框输入 ≥ 3 个字符 **When** 触发搜索 **Then** 并行查询 FatSecret API（主力）、Open Food Facts API（兜底）和本地 Room 自建食物库，FatSecret 结果优先展示（中文匹配好），OFF 结果补充，自建食物置顶，合并结果按匹配度排序。**Given** API 请求超时（> 3 秒）**When** 无网络或 API 不可用 **Then** 仅展示本地自建食物库结果，并标注「仅显示本地结果」。**Given** API 返回结果 **When** 展示列表 **Then** 每条显示食品名称、品牌、每 100g 热量、数据来源（FatSecret / OFF / 自建），点击可查看详细营养素。**Given** FatSecret API 返回空结果 **When** OFF 有结果 **Then** 自动回退展示 OFF 结果。FatSecret 需在 App 设置页标注「部分食物数据来源：FatSecret」。 | 3 天 |
| **REQ-006** | **体重记录与曲线** | P0 | **Given** 用户在仪表盘点击体重区域 **When** 进入体重记录页 **Then** 显示：① 最新体重大数字 + 与上次差值（如「-0.3kg ↓」）；② 体重变化曲线（支持 7 天/30 天/90 天切换）；③ 手动输入框（默认填入今日日期，键盘类型为数字）。**Given** 用户输入体重并保存 **When** 体重值 ≤ 目标体重 **Then** 触发 P1 里程碑检测逻辑（REQ-009 上线后联动）。 | 3 天 |

### 6.2 P1 — v1.1（4 个需求，3 周）

## 8. Non-goals（明确不做什么）

以下功能**明确不在 MVP 及后续 3 个版本范围内**。如有需求变更，需重新评估时间线和资源。

| # | Non-goal | 理由 | 替代方案 |
|---|---|---|---|
| **NG-1** | **社交功能**（好友关注、动态 feed、排行榜、饮食日记公开） | 用户研究明确结论：社交增加比较焦虑，单人场景是核心验证场景 | 仅保留「分享」按钮（里程碑卡片/体重曲线静态分享图），不建社交关系链 |
| **NG-2** | **AI 教练 / Chatbot** | MVP 阶段过度设计，LLM 调用成本不可控，与「完全免费」商业模式冲突 | P2 热量推荐引擎基于规则+简单启发式，非 LLM |
| **NG-3** | **复杂运动跟踪**（GPS 轨迹、心率带、自动运动识别、手环同步） | 手环/手表生态已饱和（Apple Health / 华为健康），与它们竞争无意义 | P3 手动运动记录仅做轻量独立模块 |
| **NG-4** | **多人/家庭组** | 用户是唯一 MVP 用户，多人协作需要权限系统、邀请流程，增加 4-6 周工作量 | 后续如有需求，重新评估时间线 |
| **NG-5** | **膳食计划 / Meal Prep** | 需要大量食谱数据和推荐算法，超出 MVP 资源 | 未来可考虑集成外部 API（如 Edamam Meal Planning） |
| **NG-6** | **Apple Health / Google Fit 集成** | 增加平台耦合度，Apple Health 需要 iOS 端，Google Fit API 权限复杂 | 仅 Android 端，手动录入体重（配合现有体重秤） |
| **NG-7** | **条形码扫描** | FatSecret 和 Open Food Facts 均支持条形码查询，但 MVP 阶段优先文本搜索；扫描功能增加开发量但使用频率不确定 | 在 REQ-005 中预留条形码搜索 API 接口，后续可快速启用 |
| **NG-8** | **水摄入记录** | 与核心差异化（采购→库存→饮食）关联度低，增加认知负担 | 无 |
| **NG-9** | **间歇性断食计时器** | 小众需求，与核心目标无关 | 无 |
| **NG-10** | **订阅/付费墙** | 0-12 个月坚持完全免费，商业模式延后考虑 | 中期可评估轻量订阅（¥4.99-6.99/月）仅覆盖 AI 深度功能 |

## 10. 待确认问题

| # | 问题 | 类型 | 阻塞 | 建议方案 |
|---|---|---|---|---|
| **Q1*** | 食物库三层架构（FatSecret + OFF + 自建）是否满足场景需求？FatSecret 中文食物覆盖率是否足够？是否需要预导入一批常见中式食物到自建库以弥补 API 缺口？ | 技术/数据 | ✅ 阻塞 REQ-005 | **建议**：开发前先手动测试 FatSecret 搜索常见中式食物（米饭、馒头、番茄炒蛋、宫保鸡丁等 20 种），评估覆盖率。如核心食物覆盖率 < 60%，需预建 50 种中式食物到自建库。工作量约 1 天 |
